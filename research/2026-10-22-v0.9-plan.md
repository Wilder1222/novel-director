# v0.9 实施方案（研究后、实现前）

## 目标和阶段结果

用户要求每阶段有正确产物。可兑现的工具契约是：每阶段确有任务专属作品、必需维度和作者要求均覆盖、证据对应确切版本、语义审查无未决项，才准推进；模型仍可能误判，不承诺客观文学正确。批准权独立保留。

| 路径 | 顺序 | 实际产物与必查内容 |
| --- | --- | --- |
| explore | brief → concept → delivery | 原话对应目标/边界；可比较备选及取舍；备选交付与停止点 |
| plan | brief → design → outline → delivery | 四维设计（规则代价/因果/人物/情感）；有序大纲及伏笔；不产生未授权正文 |
| draft | brief → scene_plan → rehearsal → draft → editorial → delivery | 带进出状态的章/场卡；真实完成排练的可读候选；完整 Run 正文；引文问题及结论；确切候选版本与残余限制 |
| revise | brief → diagnosis → revision → editorial → delivery | 原稿问题/保护范围；实际新候选及改动影响；回归审稿；版本差异与交付 |
| review | brief → diagnosis → delivery | 简报；含原文的分级问题/原因/影响与保护范围；诊断交付，不自动改稿 |
| learn | brief → exercise → feedback → delivery | 简报；选定弱项的完整原创练习/技巧与限制；原文反馈/优缺点/复练；候选交付 |
| adapt | brief → adaptation → adaptation_review → delivery | 简报；原作来源/有序场次/可拍动作/改动说明；连续性/可拍性/处理结果；改编候选交付 |
| develop | brief → research → implementation_plan → implementation → validation → delivery | 来源/限制；契约/方案/测试；实际源码改动；运行记录及失败/覆盖边界；安装与交付回执 |

每阶段提供 `work.md` 和 `index.json`（逐项锚定实际作品，不取代作品）、检查报告与审查回执。引擎保存不可覆盖的版本目录和上游门槛摘要，修改或重审使依赖的下游失效。首次输入冻结作者原话、明确要求、相关源文件和范围；允许显式新建替代流程，不伪造历史通过。

全部八条路径采用同一退出条件：实际作品完整覆盖该阶段维度，上游当前有效，全部要求/条目/标准有准确引文，独立审查无 revise/unknown/未决项，来源和预算合规。review 的退出必须有可定位问题或有证据的未发现结论，不以“没报错”称无错误；learn 的退出须有实际练习及对应反馈，不能只给训练指令；adapt 的退出须有实际改编候选与逐场可拍/承接核验，不能以场次目录取代剧本。开放创意选项可以是完整探讨产物；遗漏执行和未知正确性不能伪装成开放选项。

## 实现切片

1. 新增 `stage_gates.py` 与 `assets/stage-contracts.json`：start/packet/submit/review/status。契约必需段与逐项引文覆盖；最多 3 个版本与每版 3 次审查。原始回执和审查分开；unknown/revise/未决项不能推进；合成测试独立标记。
2. 项目内独立 `.novel_stages/` 保存流程和章节绑定，路径与现有引文模块一样拒绝链接/junction/缓存写入。冻结输入哈希；只给审查者作品、要求和相邻阶段作品，不发全量角色私密状态。上下文变更需新流程，不能自动重签旧通过。
3. 底层 Run/ensemble/assembly 入口核对已绑定章节：先有场卡才能排练，排练完成才交正文，正文核验后审稿，交付完成且候选/真实审稿匹配才准作者批准。合成流程永远不能批准/发布。旧的未绑定章节仍按原流程，显式提示不是阶段核验。
4. Studio 增加阶段绑定/转发命令，checkpoint 完成必须核对流程完成，resume 返回真实门槛。技能按自然语言意图自动选择路径，主会话构建结构，不要求作者填 JSON。工具升级也实际留下研究/方案/实现/验证/交付五类文件。
5. 文档、版本 Director 0.9.0 / Studio 0.3.0、离线示例和回归。现有 68 项继续通过；新增正反例覆盖每个门槛、过期传播、占位/漏项/错误引文/未知结论、旧入口绕过、合成污染、路径隔离、断点恢复和发布包。
6. 只读独立审查和按技能独立走查；解决发现后完整验证，刷新 manifest、生成新版本 ZIP。更新个人插件来源并使用原生安装命令，再核验实际缓存与原生技能发现。不远程 push。

## 边界和回滚

审查回执是宿主声明而非身份认证，不能证明人类、外部验收或真正上下文隔离。全覆盖引文也不证明文学优秀。真实多角色仍受既有宿主能力门槛约束；不得为过阶段伪造角色调用。旧小说、正式设定和正文保留；新模块文件和项目内新目录可独立识别。新插件安装保留旧版本来源，不删除作者工作区。

### 可执行回滚与已托管任务限制

1. 安装前保存当前插件源码目录、其 `RELEASE-MANIFEST.json`、marketplace 原文及安装列表到本轮安装回执指定的备份位置；复制前先 verify。作者 books/.studio 与 `.novel_stages` 原地保留，不回滚小说正文，不删除绑定或审查历史。
2. 需要回退时停止该任务的写入，保留当前0.9插件目录为另一份备份；用安装回执中已验证的0.8源码备份恢复**原marketplace source路径**。用系统原生单一文件操作执行，先验证两个绝对路径都属于预期插件父目录。若marketplace指向有变，再仅恢复novel-director那一项，保留其他插件。
3. 执行 `codex plugin add novel-director@personal --json` 重新安装旧来源，不手改cache；运行恢复来源的 `scripts/release.py verify`、引擎 `--version`，从新原生 `skills/list` 核对实际加载版本路径。失败时保留当前文件与错误，不报告已回退成功。
4. **0.8不认识阶段绑定，不能继续、审批或发布已经托管的0.9任务。**降级只是临时恢复旧工具，不能以其无门槛行为当作通过；在STATUS明确记阻塞，旧版仅可检查未托管旧任务。代码所有者能自行降级，旧程序无法强制理解未来契约，这不是安全隔离能力。
5. 要恢复托管任务，重新从已验证0.9来源原生安装，再用0.9 `stage-status` 与Studio `resume` 重核原有目录。源、规则或作品有变化则旧核验过期，显式建立替代流程并重审；不能删除registry或伪造通过。确需回滚正式正文另需作者本次明确授权和旧审批流程，本工具回滚不包含该动作。

以上为可操作方案，并非本轮已执行降级试验；实际安装与备份路径在后续交付回执核验。

本轮研究先行已完成。实施若改变方案，在此追加实际偏差与理由；不追写成“预先研究”。

## 实施中明确的细化

- 补齐 review/learn/adapt 三条入口路径，避免只覆盖开发和正文。
- 正文/修订scope限定单章。旧Run签名含所有正式稿，批量发布第一章会使第二章旧签名过期；本轮不增加跨章发布事务。
- 采用冻结完整故事签名的保守策略。章卡等初始结构须在stage-start前准备；修改正式源后显式新建流程，避免误把源变化当无影响。
- 修订诊断包含确切原稿全文，允许仅对该基线做初审以启动revision-plan，新的候选仍必须经过revision门槛；定向验收版本变化也使阶段过期。
- 本轮自己的升级产物在引擎实现后显式登记并接受现在的独立阶段审查；没有伪造实现前已通过的门槛记录。
